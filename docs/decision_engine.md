# Catalog Decision Engine Design

## Status

Proposed design for the first simulator decision-engine implementation.

## Objective

Implement a decision engine that starts after successful authentication and controls catalog browsing using:

- Stable user personality values.
- Dynamic mental-state values.
- Candidate-specific movie appeal.
- Current browsing-session context.

The engine chooses one of three catalog actions:

- `SELECT_MOVIE`
- `CONTINUE_BROWSING`
- `LEAVE_SESSION`

Authentication remains deterministic and outside the decision engine.

---

## Scope

This phase includes:

- Deterministic registration and login.
- Loading the movie catalog.
- Filtering eligible catalog candidates.
- Evaluating candidates.
- Calculating action scores.
- Selecting the highest-scoring action.
- Updating mental state after every action.
- Returning a selected movie or ending the session.
- Enforcing catalog-loop termination.

## Non-goals

This phase does not include:

- Real video streaming.
- Playback decision logic.
- Recommendations generated by the API.
- Persistent personality changes.
- Persisting mental state between sessions.
- Machine-learning-based decisions.

Playback will consume the selected movie in a later phase.

---

## Behavioral Principles

### Personality

Personality represents stable user characteristics and must not change during a session.

```go
type Personality struct {
	Patience      float64
	Curiosity     float64
	AttentionSpan float64
	Exploration   float64
	BingeWatching float64
	Consistency   float64
	Impulsiveness float64
}
```

### Mental state

Mental state represents temporary session conditions and changes after actions.

```go
type MentalState struct {
	Energy       float64
	Happiness    float64
	Boredom      float64
	Frustration  float64
	Immersion    float64
	Satisfaction float64
}
```

Every mental-state attribute must remain within `[0,1]`.

### Action scoring

Each action has:

- A positive drive.
- A negative pressure.

The final action score is:

```text
action score = positive drive - negative pressure
```

Scores may range from `-1` to `1`.

The action with the highest score is selected.

---

## Session State Machine

```text
START
  |
  v
REGISTER (new users only)
  |
  v
LOGIN
  |
  v
LIST_CATALOG
  |
  v
FILTER_ELIGIBLE_MOVIES
  |
  v
EVALUATE_CANDIDATE
  |
  +-- SELECT_MOVIE ------> GET_MOVIE ------> PLAYBACK_PHASE
  |
  +-- CONTINUE_BROWSING -> UPDATE_STATE ---> NEXT_CANDIDATE
  |
  +-- LEAVE_SESSION -----> UPDATE_STATE ---> LOGOUT
```

Authentication failure terminates the session before the decision engine starts.

---

## Catalog Actions

```go
type CatalogAction string

const (
	ActionSelectMovie CatalogAction = "SELECT_MOVIE"

	ActionContinueBrowsing CatalogAction = "CONTINUE_BROWSING"

	ActionLeaveSession CatalogAction = "LEAVE_SESSION"
)
```

`LIST_CATALOG` is not a decision-engine action. It is a deterministic capability call that prepares the candidates.

---

## Decision Context

The decision engine receives all information required to make one decision.

```go
type CatalogDecisionContext struct {
	Personality user.Personality

	MentalState user.MentalState

	Candidate catalog.MovieResponse

	CandidateAppeal float64

	BrowsedCount int

	MaxBrowseCount int
}
```

The engine must not perform HTTP requests or mutate the input context.

---

## Decision Result

The result includes all calculated scores for observability and testing.

```go
type CatalogDecision struct {
	Action CatalogAction

	SelectScore float64

	ContinueScore float64

	LeaveScore float64
}
```

## Candidate Preparation

After login, the session calls:

```go
movies, err := catalogCapability.ListMovies(client)
```

The session then:

1. Keeps movies with `TranscodingStatus == "READY"`.
2. Rejects movies with invalid IDs.
3. Rejects movies with `DurationSeconds <= 0`.
4. Removes duplicate movie IDs.
5. Places candidates in a seeded shuffled order.
6. Evaluates every candidate at most once.

If no eligible candidates remain, the session logs out.

---

## Browsing Fatigue

Browsing fatigue grows as candidates are evaluated.

```text
browsing fatigue =
    browsed count / maximum browse count
```

The value must be clamped to `[0,1]`.

```go
browseFatigue := clamp01(
	float64(context.BrowsedCount) /
		float64(context.MaxBrowseCount),
)
```

Browsing fatigue makes continuing less attractive and leaving more attractive.

---

## Candidate Appeal

A candidate-specific appeal value prevents every movie from producing identical decisions.

```text
candidate appeal =
    0.50 × duration fit
  + 0.30 × novelty fit
  + 0.20 × seeded attraction
```

Candidate appeal must remain within `[0,1]`.

### Duration fit

First calculate the user's watch capacity:

```text
watch capacity =
    0.60 × energy
  + 0.40 × attention span
```

Normalize movie duration using the longest eligible movie:

```text
normalized duration =
    candidate duration / maximum eligible duration
```

Then calculate duration fit:

```text
duration fit =
    1 - absolute(normalized duration - watch capacity)
```

Clamp the result to `[0,1]`.

Users with greater energy and attention span are more likely to accept longer movies.

### Novelty fit

When watch history is available:

```text
candidate previously watched:
    novelty fit = consistency

candidate not previously watched:
    novelty fit = exploration
```

When history is not yet available:

```text
novelty fit = 0.5
```

### Seeded attraction

Seeded attraction is a reproducible value in `[0,1]`.

It represents candidate-specific interest that is not yet modeled through explicit preferences.

It must come from the session-owned random generator.

---

## Select Movie Score

### Positive drive

```text
select positive =
    0.45 × candidate appeal
  + 0.20 × impulsiveness
  + 0.15 × satisfaction
  + 0.10 × happiness
  + 0.10 × (boredom × impulsiveness)
```

### Negative pressure

```text
select negative =
    0.40 × frustration
  + 0.35 × (1 - energy)
  + 0.25 × (1 - attention span)
```

### Final score

```text
select score =
    select positive - select negative
```

Candidate appeal is the strongest selection signal. Boredom only encourages selection when combined with impulsiveness.

---

## Continue Browsing Score

### Positive drive

```text
continue positive =
    0.25 × curiosity
  + 0.25 × exploration
  + 0.20 × patience
  + 0.15 × energy
  + 0.15 × (boredom × (1 - frustration))
```

### Negative pressure

```text
continue negative =
    0.35 × frustration
  + 0.30 × browsing fatigue
  + 0.20 × (1 - attention span)
  + 0.15 × (1 - satisfaction)
```

### Final score

```text
continue score =
    continue positive - continue negative
```

Boredom with low frustration encourages searching for another movie. Frustration and browsing fatigue eventually make continued browsing unattractive.

---

## Leave Session Score

### Positive drive

```text
leave positive =
    0.30 × frustration
  + 0.25 × browsing fatigue
  + 0.20 × (1 - energy)
  + 0.15 × (1 - satisfaction)
  + 0.10 × (boredom × frustration)
```

### Negative pressure

```text
leave negative =
    0.30 × curiosity
  + 0.25 × patience
  + 0.25 × candidate appeal
  + 0.20 × energy
```

### Final score

```text
leave score =
    leave positive - leave negative
```

Boredom alone does not strongly trigger leaving. Boredom combined with frustration does.

---

## Action Selection

The engine calculates all three scores and chooses the maximum.

```text
selected action =
    maximum(
        select score,
        continue score,
        leave score
    )
```

No proportional random roll is used.

### Tie resolution

Scores are considered tied when their difference is less than a small epsilon:

```go
const scoreEpsilon = 1e-9
```

When actions tie, choose between the tied actions using the session-owned seeded random generator.

This prevents source-code ordering from becoming an unintended behavioral rule.

---

## Mental-State Invariants

All mental-state mutations must use centralized helpers.

```go
func clamp01(value float64) float64 {
	return math.Max(0, math.Min(1, value))
}

func increase(value, rate float64) float64 {
	return clamp01(
		value + rate*(1-value),
	)
}

func decrease(value, rate float64) float64 {
	return clamp01(
		value - rate*value,
	)
}
```

These helpers provide diminishing changes near the boundaries.

No component should assign unbounded values directly to mental-state fields.

---

## Mental-State Transitions

### Select movie

```text
Energy       decreases by rate 0.01
Boredom      decreases by rate 0.20
Frustration  decreases by rate 0.10
Happiness    increases by rate 0.05
Immersion    increases by rate 0.10
Satisfaction increases by rate 0.10
```

This transition represents excitement and commitment after finding a suitable movie.

### Continue browsing

```text
Energy       decreases by rate 0.04
Happiness    decreases by rate 0.01
Boredom      increases by rate 0.06
Frustration  increases by rate 0.04
Immersion    decreases by rate 0.05
Satisfaction decreases by rate 0.03
```

Repeated browsing therefore becomes less attractive over time.

### Leave session

```text
Frustration  increases by rate 0.02
Immersion    decreases by rate 0.10
Satisfaction decreases by rate 0.05
```

No further decision is made after this transition.

### Personality

Personality values must never be mutated by action transitions.

## Catalog Loop

Conceptual session logic:

```go
func runCatalogLoop() (*catalog.MovieDetailsResponse, error) {
	movies, err := catalogCapability.ListMovies(client)
	if err != nil {
		return nil, err
	}

	candidates := prepareCandidates(movies)

	if len(candidates) == 0 {
		return nil, nil
	}

	maxBrowseCount := min(
		len(candidates),
		configuredBrowseLimit,
	)

	for index, candidate := range candidates {
		if index >= maxBrowseCount {
			break
		}

		appeal := decisionEngine.CalculateAppeal(
			user,
			candidate,
			candidates,
		)

		decision := decisionEngine.DecideCatalog(
			CatalogDecisionContext{
				Personality:    user.Personality,
				MentalState:    user.MentalState,
				Candidate:      candidate,
				CandidateAppeal: appeal,
				BrowsedCount:   index,
				MaxBrowseCount: maxBrowseCount,
			},
		)

		logDecision(decision)

		switch decision.Action {
		case ActionSelectMovie:
			updateMentalState(
				&user.MentalState,
				ActionSelectMovie,
			)

			movie, err := catalogCapability.GetMovie(
				client,
				candidate.ID,
			)
			if err != nil {
				applyMovieLoadFailure(
					&user.MentalState,
				)
				continue
			}

			return movie, nil

		case ActionContinueBrowsing:
			updateMentalState(
				&user.MentalState,
				ActionContinueBrowsing,
			)

		case ActionLeaveSession:
			updateMentalState(
				&user.MentalState,
				ActionLeaveSession,
			)

			return nil, nil
		}
	}

	return nil, nil
}
```

This pseudocode describes behavior, not required function names.

---

## Failure Handling

### Authentication failure

- Return the authentication error.
- Do not start the decision engine.

### Catalog list failure

- Return the catalog error.
- Logout if login succeeded.

### Empty catalog

- Treat as no available action.
- End the catalog loop.
- Logout normally.

### Movie detail failure

If `GetMovie` fails after selection:

1. Mark the candidate as unusable for the current session.
2. Increase frustration.
3. Decrease satisfaction.
4. Continue to the next candidate.
5. Return an error only if no fallback behavior is possible.

### Invalid candidate data

Invalid candidates are skipped before entering the decision loop.

---

## Termination Guarantees

The catalog loop ends when any of the following occurs:

- `SELECT_MOVIE` succeeds.
- `LEAVE_SESSION` is selected.
- All eligible candidates are exhausted.
- The maximum browse count is reached.
- The session is cancelled.
- The session timeout is reached.
- An unrecoverable API error occurs.

Mental-state changes alone are not responsible for guaranteeing termination.

---

## Randomness and Reproducibility

Every session must own its own `rand.Rand`.

A random generator must not be shared concurrently between session goroutines.

The session random generator is used for:

- Candidate shuffling.
- Candidate attraction.
- Score tie resolution.

The orchestrator should create the session seed before starting the session goroutine.

Given identical:

- Personality
- Initial mental state
- Catalog contents
- Watch history
- Session seed

the engine must produce the same candidate order and decisions.

---

## Component Responsibilities

### Session

The session:

- Performs deterministic authentication.
- Calls catalog capabilities.
- Owns the current mental state.
- Runs the catalog loop.
- Applies decision results.
- Controls session termination.
- Logs out when finished.

### Decision engine

The decision engine:

- Calculates browsing fatigue.
- Calculates candidate appeal.
- Calculates action scores.
- Selects the highest-scoring action.
- Resolves score ties.

The decision engine must not:

- Perform HTTP requests.
- Mutate personality.
- Directly control session lifecycle.
- Store global mutable state.

### Mental-state updater

The updater:

- Applies action transitions.
- Enforces the `[0,1]` invariant.
- Uses diminishing increase/decrease functions.

### Capabilities

Capabilities:

- Communicate with the API.
- Convert requests and responses.
- Return errors.

Capabilities must not decide user behavior.

## Observability

Every decision should log:

- User identifier.
- Candidate ID.
- Browsed count.
- Candidate appeal.
- Mental state before the action.
- Select score.
- Continue score.
- Leave score.
- Selected action.
- Mental state after the action.

Example:

```text
user=alice
candidate=42
appeal=0.74
select=0.51
continue=0.63
leave=-0.20
action=CONTINUE_BROWSING
```

Logging complete score information is required for tuning coefficients.

Passwords and access tokens must never be logged.

## Testing Requirements

### Candidate preparation

Test that:

- Non-ready movies are removed.
- Movies with invalid duration are removed.
- Duplicate IDs are removed.
- Candidate order is reproducible for a fixed seed.
- Every candidate is evaluated at most once.

### Candidate appeal

Test that:

- Appeal remains within `[0,1]`.
- Higher energy and attention favor longer movies.
- Exploration favors unseen movies.
- Consistency favors previously watched movies.
- Identical seeds produce identical attraction values.

### Action scoring

Test that:

- Strong appeal and impulsiveness favor selection.
- Curiosity and exploration favor continued browsing.
- Frustration and low energy favor leaving.
- Browsing fatigue reduces the continue score.
- Browsing fatigue increases the leave score.
- Every returned score is finite.

### Action selection

Test that:

- The highest score is selected.
- Ties are resolved reproducibly.
- Source-code action ordering does not resolve ties.

### Mental-state transitions

Test that:

- Select applies its expected transition.
- Continue applies its expected transition.
- Leave applies its expected transition.
- Repeated increases never exceed `1`.
- Repeated decreases never fall below `0`.
- Personality remains unchanged.

### Session integration

Test that:

- Authentication occurs before catalog loading.
- Authentication failure prevents catalog loading.
- Empty catalogs cause normal logout.
- Selection calls `GetMovie`.
- Continuing evaluates another candidate.
- Leaving causes logout.
- Candidate exhaustion causes logout.
- Browse limits prevent infinite loops.
- Movie-detail failure allows another candidate to be evaluated.

## Future Extensions

The same decision architecture can later support playback actions:

- `CONTINUE_WATCHING`
- `PAUSE`
- `SEEK`
- `STOP`
- `COMPLETE`

Playback will use different positive and negative measures while preserving:

```text
context
  → calculate action scores
  → choose highest score
  → execute action
  → update mental state
  → repeat
```

`BingeWatching` and `Immersion` will become significant during playback and post-playback decisions.
